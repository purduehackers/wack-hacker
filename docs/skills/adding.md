# Adding skills and domains

Two common paths: extending an existing domain with a new sub-skill, or standing up a whole new delegate domain. Both are SKILL.md-only operations — the domain registry, the orchestrator's delegate docs, and the context inspector's table are all generated by `compile-skills.ts`, so there is no TypeScript to edit.

## Adding a sub-skill to an existing domain

1. **Add the tool**. Create or extend a tool file under `src/lib/ai/tools/<domain>/<group>.ts`. Author it with `defineTool({ name, domain, description, access, input, execute })` and export it — `domain` matches the folder. Add it to the domain's barrel `index.ts`.
2. **Create the sub-skill**. Make `src/lib/ai/skills/<domain>/skills/<sub-skill>/SKILL.md`. In the frontmatter, list your new tool name in the `tools` array. Pick the right `minRole` (usually `organizer`).
3. **Access.** The `access: { risk, … }` field in `defineTool` is required — `risk: "destructive"` prompts for confirmation by default, and admin-only tools add `minRole: "admin"`. See [Access policy](../agents/policy.md); the `access-coverage` test fails any undeclared tool.
4. **Recompile**. Run `bun scripts/compile-skills.ts` (or just `bun run build`).

That's it — the new sub-skill will appear in the subagent's `{{SKILL_MENU}}` automatically, and `loadSkill("<sub-skill>")` will unlock the new tool when called.

## Adding a new delegate domain

1. **Create the top-level skill**. Make `src/lib/ai/skills/<name>/SKILL.md` with `mode: delegate`. Include `{{SKILL_MENU}}` somewhere in the body where the sub-skill menu should be injected (the compiler fails the build if it's missing), and declare `baseTools` — the always-visible discovery tools (typically 3–4 search/retrieve tools). Add a `routing` field if the domain needs a cross-domain tie-breaker in the orchestrator's prompt.
2. **Add tool files** under `src/lib/ai/tools/<name>/`, exporting them from a barrel `index.ts`. The compiler refuses delegate skills with no tool barrel.
3. **Create at least one sub-skill**: `src/lib/ai/skills/<name>/skills/<sub>/SKILL.md` listing the tool names it unlocks. A domain with zero sub-skills can still work, but the subagent will only ever see its `baseTools` — likely not useful.
4. **Run** `bun scripts/compile-skills.ts` to regenerate the manifests and domain registry (the build does this automatically).

That's the whole list. The generated `DOMAINS` registry wires the delegation tool, the orchestrator's system prompt documents `delegate_<name>` (with `description`, `criteria`, and `routing`) for every role that can see it, and `/inspect-context` picks up the sub-skill breakdown — no edits to `delegates.ts`, `constants.ts`, or `inspect-context.ts`.

If the domain needs non-default runtime wiring (a different model, step cap, input schema, or post-finish hook), add an entry to `DOMAIN_SPEC_OVERRIDES` in `src/lib/ai/delegates.ts` — that's the one intentionally hand-written map (it references runtime functions a compiler can't emit). See [Delegation & subagents](../agents/subagents.md).

The new `delegate_<name>` tool will appear in the orchestrator's tool list for any user whose role meets the top-level skill's `minRole`.

## Testing

- Unit-test the tool implementation under `src/lib/ai/tools/<domain>/<tool>.test.ts`. Tools are excluded from coverage thresholds, but a unit test is still the cheapest way to catch regressions.
- Drift is tested automatically: `delegates.test.ts` checks every `baseTools`/sub-skill `tools` name against the domain's barrel exports, and `orchestrator.test.ts` checks the rendered prompt against the actual delegate ToolSet.
- If the new domain introduces a new integration (auth, HTTP client, etc.), put that in `src/bot/integrations/` and test it there.
